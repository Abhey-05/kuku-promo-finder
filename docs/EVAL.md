# Evaluation

All numbers come from `npm run eval -- metrics` on the full 50-episode pack unless marked otherwise. This public file has no show text. Candidate IDs read `E<episode>-<start s>-<end s>`. Quotes and the labels themselves stay out of the repo (see the end of this file).

## Read this first

- **The labels are not from a human editor.** Claude Code labelled them while building the tool, against the brief's three tests. The builder should review them. Treat every precision number as "agreement with one judge", not as proof the promos work.
- **The same judge wrote the rules.** That inflates agreement.
- **The labelling was only partly blind.** The sheet was shuffled and hid scores, but the judge had already seen the top-10 list while tuning.
- **Samples are small.** Precision@10 rests on 10 labels, and the random baseline on 20.
- **v2 was tuned on these labels.** See below. Its numbers are not an independent test. The 6 labels added for v2 were not blind.

## Method

1. **Invariants** run as tests in `tests/engine.test.ts`, on the demo show and (when present) the full pack.
2. **Labels:** the 10 top promos of v1, plus 20 random NMS survivors split across upper, middle and lower thirds of the ranking (7, 7, 6), sampled with a fixed seed. Rule: label "post" only if the hook, the cliffhanger and the standalone test all hold.
3. **Random baseline:** the expected post rate of a uniform pick from all NMS survivors, estimated from the bands and weighted by band size. NMS survivors already sit near score peaks, so this baseline is harder to beat than a pick from all candidates.

## Held-out evaluation (v2)

The builder labels a fresh, blind sheet: `docs/labels_heldout.csv`, 30 rows (the heuristic top 10 plus 20 stratified NMS survivors, shuffled, with no scores or ranks shown). It quotes the show, so it is git-ignored. These labels were not used to tune anything. `npm run eval -- heldout` scores the heuristic, the AI-blended ranking (only when a provider key and `KUKU_ALLOW_PACK_TO_LLM=1` are set) and the random baseline on them. ### v1 against v2

v1 was the frozen engine at first labelling. Its failures led to three fixes: no clip may start on a continuation line, "freezes" now matches and hard endings are read from action entries too, and tender action counts as resolution.

| | v1 | v2 |
|---|---|---|
| Precision@5 | 40% | 80% |
| Precision@10 | 60% | 60% |
| Candidates after NMS | 241 | 237 |

The jump at 5 is two labels. Precision@10 did not move: the fixes removed bad picks, and the entries that replaced them were mixed.

### What the numbers say

- **The tool beats random at the very top:** 60% against an estimated 17.7%.
- **Below the top 10 the ranking is close to noise.** The post rate in the bands runs the wrong way: 0% upper, 14.3% middle, 33.3% lower, from 20 labels. An editor should not trust rank 40 over rank 150.
- **Hook and cliffhanger carry the ranking.** Zeroing either replaces at least 8 of the top 10. Zeroing the hook leaves none of the current top 10. The ablation is a sensitivity check only: most new entries have no label.
- **The diversity cap never fired on this pack**, because NMS plus the scoring already spread the picks.

## Main-thread responsiveness (live view)

Measured on 2026-11-08 with `scripts/live-qa.mjs` against a local production build (`vite preview`), headless Chromium on an Apple-silicon laptop, uploading the full 50-episode pack as a zip, heuristic mode. The pack was read only by the local browser and was not deployed or sent anywhere. A `PerformanceObserver` for `longtask` (tasks over 50 ms) ran from page load; a control run with a forced 300 ms block was recorded as one 300 ms task, so the observer works in this browser.

| Measure | Value |
|---|---|
| Upload to final results on screen | 3.6 s |
| Main-thread tasks over 50 ms | 0 |
| Main-thread tasks over 200 ms (target: none) | 0 |
| Longest main-thread task | under 50 ms (none recorded) |

Reading, unzipping, parsing and the pipeline all run in a Web Worker. Progress reaches the page in batches of at most about ten a second, so the page never re-renders on every event. One machine and one run: a slower device will take longer, and this is not a claim about every device.

## How the labels stay private

`docs/labels.csv` and `docs/private/` quote the show, so they are git-ignored. They are also left out of the raw outputs, because the brief wants links that open for anyone who has them. This file therefore carries IDs and neutral descriptions only. Anyone with the pack can see each failure by opening its candidate ID.
